# 镜像安全扫描（trivy）

> 适用提交：`31ddaa4` 之后 ｜ 工具：trivy（**dev 侧，非交付依赖**）｜ 复现：`make scan`
> 原则：**报告为主**——POC 阶段的第三方镜像必然带漏洞，先把风险**量化并定位到镜像**，再决定升级顺序。

---

## 1. 方法

```bash
make scan                                   # 报告模式：扫 compose 全部镜像 + 自建镜像
SCAN_FAIL_ON=CRITICAL make scan             # 发现 CRITICAL 即退出码 1（门禁模式）
SCAN_SEVERITY=MEDIUM,HIGH,CRITICAL make scan
HTTPS_PROXY=http://127.0.0.1:7897 make scan # 本机代理不通时（trivy 首跑需联网下漏洞库）
```

- 扫描对象：`docker compose config --images` 解析出的**全部运行镜像**（含 `external`/`postgres` profile）
  ＋ 自建镜像 `ssp-portal` / `ssp-soar`。
- 产物：`reports/image-scan-<时间戳>/`（每镜像一份 trivy JSON ＋ `summary.md`）；`reports/` 已 gitignore。

## 3. 关键结论

1. **自建镜像不产生风险，风险来自基础镜像**：`ssp-portal` 与 `python:3.12-slim` 的数字完全相同（0C/47H），
   `ssp-soar` 基于 `alpine:3.20` 为 **0C/0H**。→ 降低自建镜像风险 = **升级基础镜像 tag**，业务代码零改动。
2. **绝对数量集中在 4 个重栈镜像**：opensearch / dashboards / arkime / logstash 占 **61/69 的 CRITICAL、1037/1298 的 HIGH**。
   这四个是 POC 选型时的"较旧但可用"版本，是**升级收益最大**的对象。
3. **部分 CRITICAL 无修复版本（FixedVersion=`-`）**：如 arkime 的 `zlib1g`、`perl*`、`libperl5.36`
   —— 只能靠**换基础镜像/换镜像版本**解决，无法用包升级修掉。
4. 高危集中在**基础 OS 包与传递依赖**（openssl/gnutls/libxml2/musl/netty/grpc），
   平台自身业务代码是**纯标准库**，不贡献这些漏洞。

## 4. 处置路径（按性价比排序）

| 优先级 | 动作 | 说明 |
|---|---|---|
| 1 | **升级 4 个重栈镜像** | opensearch/dashboards → 2.x 最新；arkime → 较新 tag；logstash → 与 OS 对齐版本。改 compose 一行，重跑 `make verify` |
| 2 | **升级基础镜像 tag** | `python:3.12-slim` → 最新 3.12.x slim；`alpine:3.20` → 已干净可不动 |
| 3 | **不可修复项登记接受** | 对 `FixedVersion=-` 且无镜像可升的条目，逐条记录"接受理由"，避免每次扫描重复讨论 |
| 4 | **纳入版本升级流程** | 每次升级镜像/基础镜像后重跑 `make scan`，对比 `summary.md` 记录演进 |

---

## 5. 策略建议

- **默认报告模式**：`make scan` 只汇总（第三方镜像的既有漏洞不应阻断本地开发）。
- **门禁按需开启**：CI/发版前用 `SCAN_FAIL_ON=CRITICAL make scan`，并**先建基线**（把已知接受项固化），
  否则 69 条 CRITICAL 会让门禁永远红。
- **不进交付物**：trivy 是 dev 侧工具；交付物仍是 compose + 镜像 tag（未安装 trivy 时 `make scan` 自动跳过）。
