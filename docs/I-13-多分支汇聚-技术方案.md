# I-13 多分支汇聚 · 技术方案

> 状态：**已完成并实测（回归 16/16 通过）** ｜ 关联：PRD §14 范围外（R-12'）；PRD §2「千兆专线已确认，架构预留」
> 选型结论（用户拍板）：**汇聚层用 Kafka 消息总线**；分支用**独立 Filebeat 边缘代理**；告警带分支；大屏含分支状态条。
> 实现：分支 Filebeat → **Kafka(`ssp-raw`)** → 中心 Logstash(ECS 归一) → OpenSearch；分支身份 `fields.branch` → `ssp.branch`。
> 下游消费者：correlator（关联，已透传分支到告警）、portal（检索/大屏/分支健康）、I-12 资产测绘
> 并行关系：本事项与 **R-15 外部日志源适配器**共用同一「汇聚层」，二者应一并规划。

---

## 一、背景与目标

### 1.1 现状（问题）
当前 POC 是**单点采集**：一个 Filebeat 容器读本机 `logs/`，投递到中心 Logstash，产出的事件**没有任何"来自哪个分支机构"的身份**。后果：

| 问题 | 影响 |
|---|---|
| 无分支身份 | 无法按分支过滤/统计；大屏、检索、告警都看不出"是哪个分支的事" |
| 单一采集点 | 无法表达"多个分支机构各自采集、汇聚到中心"的拓扑 |
| 无分支健康 | 某分支专线断了，中心**无感知**（现有 `correlator/sources/health` 只按探针类型判活，不按分支） |

### 1.2 目标
| 目标 | 说明 |
|---|---|
| 分支身份贯穿全链路 | 事件带 `ssp.branch`，可按分支检索/聚合/下钻 |
| 多分支汇聚拓扑 | 分支侧**边缘采集代理** → 中心**汇聚层** → OpenSearch |
| 分支独立 | 任一分支断链**不影响**其他分支与平台（对齐 PRD §10「探针断连」容忍） |
| 分支注册与健康 | 业务库登记分支，中心侧按上报情况判活，前端可见 |
| 向后兼容 | 不含分支标识的既有数据默认归入 `hq`（总部），**现有回归不受影响** |
| 汇聚层可演进 | POC 轻量实现，预留消息总线接入点，供 R-15 与未来流式关联复用 |

### 1.3 非目标（本阶段不做）
- 不引入 Kafka/Flink（列为演进选项 B，见 §三）
- 不做分支侧边缘预处理/降采样
- 不做分支间数据隔离的多租户（POC 为单一中心）
- 不改造 Arkime（其直连同一 OpenSearch，本事项不动它）

## 三、汇聚层形态对比

| | A 轻量（Filebeat → Logstash） | B 消息总线（Kafka） | C 先 A 预留 B |
|---|---|---|---|
| 新增组件 | 无 | Kafka（+ZooKeeper/KRaft） | 无（预留配置位） |
| 削峰/缓冲 | 弱（Logstash 停机即断） | 强（Kafka 落盘） | 弱 |
| 断链重放 | 分支本地 spool 有限 | 支持按位点重放 | 同 A |
| 多消费者 | 无 | 支持（关联/测绘/归档并发消费） | 后续 |
| 运维复杂度 | 低 | 中—高 | 低 |
| 与 R-15 / 流式关联 | 需改造 | 天然共用 | 后续平滑 |
| POC 结论 | ✅ 可落地 | ✅ **已选（用户拍板）** | ⏳ 备选 |

> **为什么选 B**：多分支机构属于"边缘到中心"的跨域汇聚，链路抖动/专线中断是常态。Kafka 提供**落盘缓冲 + 按位点重放 + 多消费者**，
> 且同一主题天然成为 R-15 外部日志源适配器与未来流式关联的统一入口。分支侧只需配置 `output.kafka`，中心侧只需一个 `kafka` input。
> **演进说明**：`beats` 直连入口予以保留（旁路/调试/适配器直投），两条入口事件结构一致。

## 五、数据模型

### 5.1 事件字段扩展（`config/opensearch/ssp-ecs-template.json`）

新增 `ssp` 命名空间（显式 keyword，避免依赖动态映射）：

```json
"ssp": {
  "properties": {
    "branch":      { "type": "keyword" },
    "branch_site": { "type": "keyword" }
  }
}
```

- 索引 `index_patterns` 不变（`ssp-suricata-*` / `ssp-zeek-*` / `ssp-wazuh-*`）。
- 模板 `priority: 100`，下发脚本 `scripts/apply-ecs-template.sh` 已有；**已存在的日索引需 reindex 或等待新索引**（POC 直接重置索引重放即可）。

### 5.2 告警字段扩展（`config/opensearch/ssp-alerts-template.json`，`dynamic:false`）

在既有 `ssp` 块内新增：

```json
"branch": { "type": "keyword" }
```

> ⚠️ 该模板 `dynamic:false`：**不显式声明就会被静默丢弃**（项目已知坑）。correlator 需从贡献事件读取 `ssp.branch` 并写入告警。

### 5.3 业务库新表 `branches`（`services/portal/db.py`）

| 列 | 类型 | 说明 |
|---|---|---|
| `branch_id` | TEXT PK | 分支标识，如 `hq` / `sh-01` / `bj-01`（= 事件里的 `ssp.branch`） |
| `name` | TEXT | 分支名称（如「上海分行」） |
| `site` | TEXT | 站点/机房 |
| `cidr` | TEXT | 该分支网段（逗号分隔，供资产测绘归属参考） |
| `link_type` | TEXT | `leased`（专线）/ `vpn` / `internet` |
| `enabled` | INTEGER | 1 启用 / 0 停用（停用则不参与判活告警） |
| `expect_interval_seconds` | INTEGER | 期望上报间隔（超过即判 `stale`） |
| `last_seen` | INTEGER | 最近一次收到该分支事件的 epoch 秒 |
| `state` | TEXT | `ok` / `stale` / `no_data` / `disabled` / `unregistered` |
| `note` | TEXT | 备注 |
| `created_at` / `updated_at` | INTEGER | 时间戳 |

> 迁移沿用 I-12 的 `_ensure_columns()` 同款思路：`SCHEMA_SQL` 加 `CREATE TABLE IF NOT EXISTS branches`（幂等），`init_schema()` 自动建表。

### 5.4 分支状态判定口径（D4）

| 状态 | 条件 |
|---|---|
| `ok` | 期望窗口内 `doc_count > 0` 且 `now - max(@timestamp) ≤ expect_interval_seconds × 2` |
| `stale` | 有数据但最近上报超出期望间隔 ×2（链路慢/探针停） |
| `no_data` | 期望窗口内 `doc_count == 0`（视同断链） |
| `disabled` | `enabled = 0` |
| `unregistered` | 事件里出现了**未登记**的 `ssp.branch`（提示补登记） |

## 六、采集与打标实现

### 6.1 Filebeat（分支边缘代理）

**分支代理**（新增 `deploy/branch/filebeat-branch.yml`，由环境变量参数化分支 ID）：

```yaml
filebeat.inputs:
  - type: filestream
    id: suricata-eve
    paths: ["/var/log/branch/suricata/*.json"]
    fields: { log_source: suricata, branch: "${BRANCH_ID}" }
  - type: filestream
    id: zeek-logs
    paths: ["/var/log/branch/zeek/*.log"]
    exclude_lines: ['^#']
    fields: { log_source: zeek, branch: "${BRANCH_ID}" }
  - type: filestream
    id: wazuh-alerts
    paths: ["/var/log/branch/wazuh/*.json"]
    fields: { log_source: wazuh, branch: "${BRANCH_ID}" }
output.kafka:
  hosts: ["kafka:9092"]
  topic: "ssp-raw"
  required_acks: 1
  compression: gzip
```

**总部代理**（现有 `deploy/filebeat/filebeat.yml`）：各 input 的 `fields` 增加 `branch: hq` / `branch_site: 总部`，
并把 `output.logstash` 改为 `output.kafka`（同一 `ssp-raw` 主题）。

### 6.2 Logstash（中心汇聚 + 打标）

1. **入口改为 Kafka**（`config/logstash/conf.d/00-inputs.conf`）：

```ruby
input {
  kafka {
    bootstrap_servers => "kafka:9092"
    topics            => ["ssp-raw"]
    group_id          => "ssp-logstash"
    auto_offset_reset => "earliest"
    codec             => json      # Filebeat 事件 JSON → 字段直接可用
    tags              => ["ssp-kafka"]
  }
  beats { port => 5044  tags => ["ssp-beats"] }   # 兼容直连入口（旁路/调试/R-15）
}
```

2. **分支打标**（新增 `config/logstash/conf.d/05-branch.conf`，在归一之前执行，仅做字段提升，不动既有 10/20/30）：

```ruby
filter {
  # 分支身份：Filebeat fields.branch → ssp.branch；缺失则归总部
  if [fields][branch] {
    mutate { add_field => { "[ssp][branch]" => "%{[fields][branch]}" } }
  } else {
    mutate { add_field => { "[ssp][branch]" => "hq" } }
  }
  # 站点名映射（可由 config 表下发；POC 先用静态小字典）
  mutate {
    add_field => { "[ssp][branch_site]" => "%{[fields][branch_site]}" }
  }
}
```

> 说明：分支区分是**逻辑的**（靠字段），不是物理端口——新增分支只需加一个边缘代理并复用同一 `ssp-raw` 主题，
> 中心侧**无需改端口/防火墙/管道**。Kafka 即插入点：R-15 适配器与未来流式消费者可并发消费同一主题。

### 6.3 correlator 透传分支（D5）

- `fetch_events()` 已按 `fields.log_source` 白名单过滤；新增：把贡献事件的 `ssp.branch` 收集为集合。
- 写告警时补 `ssp.branch`（单分支）与 `related.branches`（跨分支时，keyword 数组）。
- 需同步在告警模板显式声明这两个字段（见 §5.2）。

## 七、分支健康监测（portal 进程内）

复用 I-12 的"进程内后台线程"模式（**不新建服务**，避免跨进程业务库锁竞争）：

- 线程名 `branch-health`，间隔 `BRANCH_HEALTH_INTERVAL_SECONDS`（默认 `300`，`0`=关闭）。
- **单次**探测（与 correlator `source_health` 同思路，用**相对陈旧度**而非绝对当前时间，历史数据重放同样适用）：

```
POST /ssp-events/_search
{ "size": 0,
  "aggs": { "tmax": { "max": { "field": "@timestamp" } },
            "b": { "terms": { "field": "ssp.branch", "size": 200 },
                   "aggs": { "last": { "max": { "field": "@timestamp" } },
                             "cnt":  { "value_count": { "field": "@timestamp" } } } } } }
```

- 判定：令 `T = tmax`（全局最新事件），对每个**已登记**分支——`enabled=0` → `disabled`；
  不在聚合里 → `no_data`；`T - last > expect_interval_seconds` → `stale`；其余 → `ok`。
  聚合里出现但未登记 → 列表中以合成条目提示 `unregistered`（不写库、不阻断入库）。
- 结果写回 `branches.state` / `last_seen`。
- OpenSearch 不可达 → 本次探测失败只记日志，**不改变已有状态、不影响平台其他功能**（对齐 PRD §10）。

## 十一、验收（EARS 风格 + 用例 + 实测结果）

**EARS**
- **Event-driven**：当分支代理投递事件，系统应在入库事件上标注 `ssp.branch`；未携带分支标识的存量链路应默认归入 `hq`。
- **Ubiquitous**：系统应支持按 `ssp.branch` 检索与聚合（term 过滤 / terms 聚合均可用）。
- **State-driven**：当某分支在期望窗口内无事件上报，系统应将该分支标记为 `no_data`，而**其他分支状态与事件量不受影响**。
- **Unwanted**：若 OpenSearch 不可达，分支健康探测应失败但不影响平台其他功能，且不误改分支状态。
- **Event-driven**：当出现未登记的 `ssp.branch`，系统应提示 `unregistered`（不阻断入库）。
- **State-driven**：当分支被停用（`enabled=0`），系统应标记 `disabled` 且不参与离线告警。

**用例（已实现于 `scripts/test-cases.py`）**

| 编号 | 类型 | 场景 | 期望 |
|---|---|---|---|
| A13 | 正例 | 分支数据入库后聚合/过滤 | 三分支（hq/sh-01/bj-01）均可聚合；term 过滤命中数与聚合一致；`ssp.branch_site` 正确 |
| A14 | 正例 | 登记 + 探测 + 停用 | 三分支 `ok`；停用 bj-01 → `disabled`；恢复 → `ok` |
| A15 | 正例 | 模拟 bj-01 断链（清其事件） | bj-01 → `no_data`；sh-01 / hq 仍 `ok` 且**事件量不变**；重建代理后数据回填 |

## 十二、风险与限制

| 风险 | 影响 | 对策 |
|---|---|---|
| Logstash 中心单点 | 归一层停机即断采 | **Kafka 已提供落盘缓冲**：Logstash 短暂停机不影响分支投递，恢复后按位点续读；生产可横向扩消费者 |
| Kafka 单节点（POC） | broker 挂了汇聚中断 | POC 单节点 KRaft；生产用 3 副本集群（`KAFKA_*_REPLICATION_FACTOR` 已集中配置） |
| Kafka 磁盘增长 | 长期占用磁盘 | 主题保留 24h（`KAFKA_LOG_RETENTION_HOURS`），并挂 named volume 限制在项目数据卷内 |
| 告警模板 `dynamic:false` | `ssp.branch` 被静默丢弃 | 显式声明字段（§5.2），并加回归断言 |
| 已存在日索引无新字段 | 旧索引缺 `ssp.branch` | 重置索引重放（POC 常用做法）；生产用 reindex |
| 分支身份靠字段、非物理隔离 | 误标/伪造分支 | POC 内网可信；生产用 mTLS/独立入口 + 分支级鉴权（列入后续） |
| 分支健康判定为"事后感知" | 断链不能秒级发现 | 判活窗口/期望间隔可配（`expect_interval_seconds`）；后续可加分支侧心跳 |
| 与 R-15 关系 | 两条需求都想改采集层 | **共用本汇聚层**：R-15 适配器输出同样打 `fields.log_source`/`fields.branch` 即可复用 |
