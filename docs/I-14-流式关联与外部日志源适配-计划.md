## 一、背景与机会

1. **Kafka 汇聚层已在位**（I-13）：所有分支 + 总部的事件都经 `ssp-raw` 主题汇聚，再做 ECS 归一。
   这意味着"实时消费事件流"这件事的**采集侧已零成本就绪** —— 只需新增消费者。
2. **当前关联是批式**：`correlator` 按窗口扫描 OpenSearch（`POST /correlate` 或定时），
   告警时延取决于扫描周期，属**分钟级**；跨源关联要等事件落库后才可能命中。
3. **外部日志源尚未接入**：防火墙 / WAF / syslog / AD 等第三方源的日志还进不来，
   攻击面覆盖不完整（PRD §14 的 R-15 需求）。

**结论**：两条路线都指向同一个已建成的汇聚层，属于"边际成本最低、收益明确"的下一步。

## 五、关键设计要点

1. **消费位点**：消费者组 `ssp-stream`，位点由 Kafka 管理（`auto.offset.reset=latest` 用于实时，
   `earliest` 仅用于重放）；重放与实时用**不同 group_id** 隔离，避免互相影响。
2. **与批式共存**：流式负责"秒级初判"，批式负责"窗口内跨源深度关联"。二者写同一索引，
   靠 `ssp.alert.id = sha1(rule_id + entity_key)` **幂等去重**（沿用现有约定）。
3. **分支维度**：告警继续透传 `ssp.branch` / `related.branches`（I-13 已建），
   使大屏可按分支看实时告警。
4. **窗口以事件时间为准**：沿用 I-13 的经验——窗口锚定事件时间而非墙钟，
   否则历史数据重放会全部落在窗口外（这是本项目已经踩过的坑）。
5. **外部源适配层**：适配器只做"解析 + 打标"，**不做归一**（归一仍统一在 Logstash），
   与现有分工一致（Filebeat 只投递 → Logstash 归一）。

## 七、验收标准（EARS + 用例）

**EARS**
- **Event-driven**：当 `ssp-raw` 出现新事件，系统应在秒级内完成规则匹配并把命中写入 `ssp-alerts`。
- **Ubiquitous**：流式与批式写入同一索引时，同一 `(rule_id, entity_key)` 应只产生一条告警（幂等）。
- **Unwanted**：若流式消费者中断，应自动重连并从位点续读，**不丢事件、不重复计费式放大**；
  且不得影响批式 correlator、测绘、大屏等既有功能。
- **Event-driven**：当外部源（如防火墙）投递日志，系统应打上 `fields.log_source` 与 `fields.branch` 后入库，
  并可被检索与关联消费。
- **State-driven**：当外部源适配器处于关闭状态（默认），系统应不产生任何副作用。

**用例（拟加入 `scripts/test-cases.py`）**

| 编号 | 类型 | 场景 | 期望 |
|---|---|---|---|
| A16 | 正例 | 流式关联端到端 | 事件入 Kafka 后 ≤ 5s 内 `ssp-alerts` 出现对应告警，且带 `ssp.branch` |
| A17 | 正例 | 幂等与共存 | 流式 + 批式先后命中同一实体 → 告警总数不重复增长 |
| N12 | 反例 | 消费者中断 | 停消费者 → 恢复后位点续读，事件不丢；批式与大屏不受影响 |
| N13 | 反例 | 外部源关闭 | 适配器关闭时无额外事件入库、无异常日志 |

## 八、风险与依赖

| 风险 | 影响 | 对策 |
|---|---|---|
| Flink 在 x86 私有化的交付复杂度 | 部署/运维成本上升 | 先走 C（轻量消费者），接口预留引擎替换点 |
| 流式与批式规则实现分叉 | 行为不一致、维护双份 | 规则定义抽成**共享配置**，两侧只做执行 |
| 消费位点管理不当 | 重放导致告警重复或事件丢失 | 实时/重放分组隔离；幂等 `_id`；位点落盘可观测 |
| 外部源方言多样 | 解析工作量不可控 | 先做 1 类源（D3 定），其余按需增量 |
| 时延目标过紧 | 验收争议 | POC 目标 ≤5s 并实测留证；生产目标另行商定 |

**依赖**：I-13（Kafka 汇聚层）✅ 已完成；`ssp-alerts` 模板可用 ✅；MISP 情报接口 ✅。
